# Photo Review

[English](#english) | [繁體中文](#繁體中文)

<a id="english"></a>

## English

A two-stage triage bench for a photo library that is too large to open one file at a time.
Scroll through a folder in the browser, rate and tag each photo with a single keystroke, then
write the result back into Darktable sidecar files so the ratings survive outside this tool.

Built for a personal library of roughly 70,000 photos, where opening each one in a full editor
was the bottleneck.

### How it works

**Stage 1 — fast pass.** `generate.py` scans a folder and builds a single HTML page. Photos are
referenced with `file://`, never copied, so a few hundred images stay responsive through lazy
loading. HEIC and RAW files, which no browser renders, get a JPEG preview generated by the
built-in macOS `sips` and `qlmanage`; previews live in a cache folder and the originals are
never touched.

In the page: scroll for the next photo, click or press `0`–`5` to rate, `X` to mark for deletion
(recorded only, nothing is deleted), and `F` to jump to a free-text note field, which pairs well
with system dictation. Tag buttons come from a controlled vocabulary, each bound to a letter key.
Everything is saved to `localStorage` as you go, so closing the tab loses nothing.

**Stage 2 — confirmation.** Export a JSON file and hand it to an assistant that cleans up the
dictated notes and proposes a rating, colour label and tag set per photo. `confirm_page.py`
renders those proposals as a second page: cards the assistant changed are yellow, untouched ones
are green, and every field stays editable. Confirming produces the final JSON.

**Landing.** `apply.py` moves photos marked for deletion to the system trash, never `rm`, and
appends every kept photo to a searchable CSV diary. It is a dry run by default; `--apply` is
required to touch anything. `write_xmp.py` then writes Darktable-compatible `.xmp` sidecars.

### Design decisions worth reading

- **Sidecars are merged, not overwritten.** Darktable is often configured to write a `.xmp` the
  moment a photo is imported, so "skip files that already have a sidecar" silently does nothing
  at all. This tool merges only the rating, colour label and tag fields, leaving edit history and
  EXIF untouched. If a field already holds a different value, that one field is left alone and
  the conflict is reported.
- **A controlled vocabulary, not free text.** Free typing splits one idea across `Tokyo`,
  `tokyo` and `東京`. Tags are picked from a list in a Markdown file; new terms typed during a
  session are written back to it by `lint.py --add-new-terms`, and `rename_tag.py` renames a term
  across both the CSV and every sidecar so nothing is left pointing at the old spelling.
- **Nothing destructive happens without a dry run first.** `apply.py`, `split_by_date.py` and
  `rename_tag.py` all preview by default and back up before writing.
- **Dates come from EXIF, never from file modification time.** Files whose capture date cannot be
  read go to a separate folder rather than being guessed at.

### Layout

The folders are the pipeline. Each stage of the workflow is its own subpackage, so the
directory listing tells you how the tool thinks.

```
photo_review/
├── config.py        the single authority on paths: where photos live, where records go
├── vocab.py         the controlled vocabulary
├── gpsread.py       EXIF coordinates, or None — never guessed
├── templates/       the review page and the confirmation page
├── review/          stage 1  build the page, re-render old pages after a layout change
├── confirm/         stage 2  consistency checks, build the confirmation page
├── land/            stage 3  trash, diary CSV, Darktable sidecars
└── library/         library upkeep: index, progress, relocate, rename, split, reconcile
tests/               14 tests; they synthesise their own photos and need no drive attached
```

Every module is runnable on its own:

```bash
python3 -m photo_review.review.generate <folder> --no-open
python3 -m photo_review.library.progress
python3 tests/test_photo_review.py
```

### Getting started

Requires Python 3.9+ and macOS for the preview generation and trash behaviour.

```bash
cp config.example.json config.local.json   # then edit the paths inside
python3 -m photo_review.config             # check what it resolved to
python3 test_photo_review.py               # 14 self-tests, no photos needed
python3 generate.py "/path/to/a/folder" --no-open
```

`config.local.json` holds every machine-specific path — where the photos live, where the CSV
records go, which vocabulary file to read. Nothing else in the codebase hardcodes a location, so
the same code runs unchanged on another machine.

### Files

| File | Role |
|---|---|
| `config.py` | Resolves every path; environment variable → `config.local.json` → `config.example.json` |
| `generate.py` / `template.html` | Stage 1: folder → review page |
| `confirm_page.py` / `template2.html` | Stage 2: proposals → confirmation page |
| `apply.py` | Trash the rejects, append the keepers to the CSV diary |
| `write_xmp.py` | Write Darktable sidecars, merging into existing ones |
| `vocab.py` / `vocab.example.md` | The controlled tag vocabulary |
| `lint.py` | Consistency checks before landing; warns, never blocks |
| `rename_tag.py` | Rename one tag across the diary and the sidecars |
| `locate.py` | Where did the photos go, and did the sidecars follow |
| `progress.py` / `make_index.py` | Which folders are done, which are not |
| `split_by_date.py` | Split a camera dump into `YYYYMMDD/` folders by EXIF date |
| `gpsread.py` | Read capture coordinates using only the standard library |
| `test_photo_review.py` | Self-tests using synthetic images in a temp folder |

## 繁體中文

一個兩階段的照片初篩台,給「多到沒辦法一張一張打開」的照片庫用。
在瀏覽器裡滾輪逐張看,一個按鍵完成評分與標籤,最後把結果寫回 Darktable 讀得懂的評分檔,
資料不會被鎖在這個工具裡。

當初是為了一個約七萬張的個人照片庫寫的 —— 瓶頸在於「每張都要用修圖軟體打開」。

### 怎麼運作

**第一階段:快速掃過。** `generate.py` 掃一個資料夾,產出一頁 HTML。照片用 `file://` 直接指向原圖,
不複製、不搬動,靠延遲載入讓幾百張也滾得順。HEIC 與 RAW 瀏覽器看不了,就用 macOS 內建的
`sips` / `qlmanage` 產一張 JPG 預覽放進快取夾,**原始照片一個位元都不碰**。

頁面裡:滾輪往下就是下一張,點星星或按 `0`–`5` 評分,按 `X` 標記想刪的(只記錄,不會真的刪),
按 `F` 跳到心得框,搭配系統的語音聽寫很順。標籤按鈕來自一份固定用語表,每個詞綁一個字母鍵。
邊評邊存在瀏覽器裡,關掉分頁不會掉。

**第二階段:確認。** 匯出 JSON 交給 AI,它把口述的心得整理通順,並替每張提案星等、顏色標、標籤。
`confirm_page.py` 把提案渲染成第二頁:AI 改過的卡片黃底、沒動的綠底,每一欄都還可以改。
按下確認就產出最終的 JSON。

**落地。** `apply.py` 把標記刪除的照片丟進系統垃圾桶(⛔ 不用 `rm`),把留用的寫進可搜尋的 CSV 日記總表。
預設是乾跑,要加 `--apply` 才會真的動。接著 `write_xmp.py` 寫出 Darktable 相容的 `.xmp` 評分檔。

### 幾個值得一看的設計決定

- **評分檔是「併入」不是「覆蓋」。** Darktable 常常設定成「照片一匯入就寫一份 `.xmp`」,
  所以「已經有評分檔就跳過」這種寫法**等於整批都不寫,而且不會報錯**。
  這支只併入星等、顏色標、標籤三欄,修圖步驟與 EXIF 原封不動;
  那三欄已經有不同的值 → 那一欄不動,並把衝突列出來。
- **用固定用語表,不讓人自由打字。** 自由打字會讓同一件事裂成 `Tokyo` / `tokyo` / `東京`。
  標籤從一份 Markdown 清單裡點選;當場打的新詞由 `lint.py --add-new-terms` 寫回那份清單;
  `rename_tag.py` 可以把一個詞在 CSV 與所有評分檔裡一次改名,不會留下指著舊寫法的殘骸。
- **會破壞東西的動作一律先乾跑。** `apply.py`、`split_by_date.py`、`rename_tag.py`
  預設都只預覽,真的要寫之前先備份。
- **日期只認 EXIF,⛔ 不用檔案修改時間猜。** 讀不到拍攝日期的照片放進另一夾,不猜。

### 資料夾怎麼分

**資料夾就是工作流。** 每個階段自己一個子套件,所以光看目錄就知道這支工具怎麼想事情。

```
photo_review/
├── config.py        路徑的唯一權威:照片在哪、紀錄寫到哪
├── vocab.py         固定用語表
├── gpsread.py       讀 EXIF 座標,讀不到就是 None,⛔ 不編造
├── templates/       審片頁與確認頁的樣板
├── review/          ① 初篩:產審片頁;版面改了把舊頁重產
├── confirm/         ② 確認:一致性檢查、產確認頁
├── land/            ③ 落地:丟垃圾桶、寫日記總表、寫 Darktable 的 .xmp
└── library/         照片庫維護:首頁索引、進度、找檔、標籤改名、按日期分夾、匯出對帳
tests/               14 項測試,自己造合成照片,不需要插任何硬碟
```

每一支都可以自己跑:

```bash
python3 -m photo_review.review.generate <資料夾> --no-open
python3 -m photo_review.library.progress
python3 tests/test_photo_review.py
```

### 開始用

需要 Python 3.9 以上;預覽產生與垃圾桶的行為需要 macOS。

```bash
cp config.example.json config.local.json   # 然後改裡面的路徑
python3 -m photo_review.config                          # 看它實際讀到什麼
python3 test_photo_review.py               # 14 項自我測試,不需要任何照片
python3 generate.py "/照片資料夾的路徑" --no-open
```

`config.local.json` 是唯一放機器相關設定的地方 —— 照片在哪、紀錄寫到哪、讀哪份用語表。
程式碼裡沒有任何寫死的位置,所以同一份程式換一台電腦可以直接跑。
